# Приоритеты, архитектурные требования, журнал изменений

## Приоритет

| ID | Приоритет | Почему так |
|---|---|---|
| FR-04, FR-05, FR-06 | P0 | Нет ответа и нет удержания баланса — нет продукта |
| FR-02, DR-01, DR-02, NFR-02, NFR-05 | P0 | Ключ и проводка — часть того же среза |
| FR-01, FR-03, FR-07 | P1 | Нужны, чтобы срезом мог пользоваться человек, но mock-ключ и ручное начисление не блокируют первый вызов адаптера |
| FR-08, NFR-01, NFR-03, NFR-04 | P1 | Каталог из двух моделей и замер stage. Не блокируют первую генерацию |
| DR-04 | P1 | Пока себестоимость в одной валюте с ценой клиента, курс не на критическом пути. Правило уже зафиксировано |
| NFR-06, DR-05, DR-06, DR-07, DR-08 | P2 | Сопровождение и защита от мусора, проверяются вместе с OpenAPI |

## Архитектурно значимые требования

Эти пункты нельзя выполнить «любым» сервисом в одном процессе без записи. Они ограничивают разложение системы.

| ID | Требование | Ограничение |
|---|---|---|
| ASR-01 | NFR-02 и FR-06: списание ровно одно, RPO ledger = 0 | Ledger в PostgreSQL, коммит проводки до подтверждения списания клиенту. Повтор генерации идемпотентен |
| ASR-02 | FR-04 и каноническая схема | Адаптер провайдера отделён от HTTP-контракта клиента. Новый провайдер не меняет тело `POST /v1/chat/completions` |
| ASR-03 | NFR-05 | Секреты не в таблицах usage и не в логах. Отдельное хранение секрета, в ответе API секрета нет |
| ASR-04 | DR-01 и объём журнала | Usage — событие без текста промпта, витрина аналитики не в той же базе, что проводки. В бэклоге это ClickHouse, `ID24_API-129` |
| ASR-05 | NFR-01 | Время провайдера не смешивается с накладными расходами шлюза: замер идёт через mock, таймаут провайдера задаётся отдельно |

## Как меняются требования

1. Любой участник заводит карточку в бэклог со ссылкой на ID требования и предлагаемой правкой.
2. Смысл для клиента и приоритет подтверждает Улитин Максим. Если правка затрагивает ASR, её дополнительно подтверждает Ерофеев Илья.
3. Принятая правка попадает в этот каталог новой записью журнала и в критерии приёмки связанной задачи. Старый ID не переиспользуется: отмена помечается как снято.
4. В текущий спринт изменение попадает только решением тимлида, как и любая новая карточка.

Связь с доской: у задачи в «Сфере» в описании стоит ID требования, которое она закрывает. Закрытие задачи не меняет текст требования само по себе.
