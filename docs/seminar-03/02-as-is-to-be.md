# AS-IS и TO-BE

Ключевой процесс: разработчик получает ответ модели и понятную стоимость этого ответа.

## AS-IS

Сейчас шлюза нет. Разработчик сам заводит кабинет у каждого провайдера.

1. Выбирает модель и читает её контракт. У Anthropic, Gemini и OpenAI тела запросов разные.
2. Выпускает ключ в кабинете провайдера и кладёт его в своё приложение.
3. Пишет обработку ошибок, таймаутов и повторов под этого провайдера.
4. Когда провайдер недоступен, вручную переключает модель или ждёт.
5. Считает токены по тарифу этого кабинета. Счета в разных валютах, закрывающие документы — отдельно у каждого поставщика.
6. Чтобы сменить модель, меняет код клиента.

Сбой виден только в логах приложения. Общего баланса и журнала по ключам нет. Секрет провайдера лежит у клиента.

## TO-BE

Тот же разработчик подключает NeuroGateway один раз.

1. Регистрируется, выпускает один ключ шлюза, пополняет баланс в рублях. На MVP пополнение — заглушка, сумма появляется на балансе без эквайринга (`ID24_API-98`).
2. Шлёт `POST /v1/chat/completions` с именем модели. Контракт один (`ID24_API-25`, `ID24_API-49`).
3. Шлюз проверяет ключ и лимит, ставит hold, выбирает живой endpoint провайдера, при обрыве уходит на запасной, если клиент это разрешил.
4. Возвращает ответ и заголовки `X-Request-Id` и `X-Generation-Id`.
5. Списывает фактические токены проводкой и снимает hold. Клиент видит расход по ключу в журнале, без текста промпта.
6. Смена модели — это другое имя в том же запросе, а не новый SDK.

AS-IS заканчивается на стороне разрозненных кабинетов провайдеров. TO-BE переносит выбор провайдера, повтор, учёт токенов и рублёвый баланс в шлюз. Клиент больше не хранит ключи провайдеров, кроме будущего режима BYOK, которого нет в Release 0.5.
